# Telegram Auto Poster Bot

Телеграм-бот для отложенного и автоматического постинга в канал.
Админы присылают контент боту — бот кладёт его в очередь и публикует в заданное время с заданным интервалом. Есть статистика, роли админов и поддержка именных ботов.

---

## Возможности

* 📥 Приём сообщений (фото / видео / файлы) от админов
* ⏳ Очередь постов (SQLite)
* ⏰ Автопостинг по времени и интервалу
* 🎯 Рандомный выбор админа для публикации
* 🤖 Поддержка **именных ботов** для разных админов
* 📊 Статистика: опубликовано, в очереди, просмотры, реакции
* 🔁 Автосброс статистики по расписанию
* 🛠 Управление через команды Telegram

## Переменные окружения (`.env`)

**Звёздочкой * выделены те переменные, которые необходимо вставить напрямую в .env перед введением бота в эксплуатацию**

```env
*BOT_TOKEN=12345:qwerty          # токен основного бота
*CORE_API_ID=12341234            # api_id Telegram (telethon) — необходимо для сбора статистики админов 
                                 # и постов
*CORE_API_HASH=abcdef123456      # api_hash Telegram — необходимо для сбора статистики админов и постов
*ADMIN_UNS=ivan,petya,egor       # админы (username без @) — первая позиция - генеральный админ с доступом
                                 # ко всем командам
*CHANNEL_ID=-12345               # ID канала для постинга

BOT_MAPPINGS=                  # <bot_token>:<username>,... — заполняется через команду /addbot

# время начала и конца сессии можно установить через команду /settime
START_HOUR=0
START_MINUTE=0
END_HOUR=23
END_MINUTE=59

POSTING_INTERVAL=60             # интервал постинга (сек) можно установить через команду /setinterval
RESET_INTERVAL_DAYS=7           # интервал сброса статистики можно установить через команду /resetstattime
```

### BOT_MAPPINGS

Позволяет публиковать посты **от имени разных ботов**:

```env
BOT_MAPPINGS=111:ivan,222:petya
```

Если у админа нет именного бота — используется основной.

## Запуск

### Локально

```bash
python bot.py
```

### Docker

```bash
docker compose up -d --build
```

> **Важно перед первым запуском в Docker:**
> Создай пустые файлы на хосте, иначе Docker смонтирует папки вместо файлов:
> ```bash
> touch runtime_data.json messages.db statistics.db
> ```
>
> Telethon требует интерактивной авторизации при первом запуске (номер телефона + код из Telegram).
> Docker-контейнер не поддерживает интерактивный ввод, поэтому нужно:
>
> 1. Запустить бота **локально** один раз: `python bot.py`
> 2. Пройти авторизацию Telethon (введи номер телефона и код)
> 3. Убедиться что появились файлы `*.session` в папке проекта
> 4. Только после этого запускать `docker compose up -d --build`
>
> При переносе на новый сервер — скопируй `.session` файлы вместе с `.env`.

**Убить зависший контейнер:**

```bash
bash scripts/remove_stuck_container.sh
# или с явным ID:
bash scripts/remove_stuck_container.sh abc123
```

## Команды бота

### Общие (админы)

* `/help` — список команд
* `/messages` — сохранённые сообщения
* `/clear` — очистить свою отложку с подтверждением; опубликованные посты сохраняются
* `/cancel` — отменить запрос на очистку

После `/clear` бот показывает владельца очереди и число сообщений. Для удаления
нужно в течение 2 минут отправить в том же чате отдельное текстовое сообщение
`да, я подтверждаю` от того же пользователя. Права проверяются повторно.
Если подтверждение не получено за 2 минуты, запрос автоматически отменяется,
а бот отправляет в тот же чат сообщение: «Время подтверждения истекло.
Очистка отменена, бот работает в обычном режиме».
Удаляются только сообщения, которые были в очереди при запросе и ещё не опубликованы;
добавленные позже сохраняются. Элементы альбома считаются отдельными сообщениями.
Повторный `/clear` заменяет предыдущий запрос. После перезапуска бота запрос нужно повторить.
Обычному админу доступен только `/clear` без аргументов; указать username может только главный админ.

### Главный админ

* `/post <id>` — принудительно выложить пост
* `/settime HH:MM HH:MM` — время постинга
* `/setinterval <sec>` — интервал постинга
* `/resetstattime <days>` — интервал сброса статистики
* `/stat` — статистика админов
* `/config` — текущая конфигурация
* `/clear username` или `/clear @username` — очистить отложку конкретного админа с подтверждением; `/clear` без аргумента очищает свою
* `/clearposted` — удалить из базы опубликованные посты (например, при смене канала)
* `/collectstats` — принудительно запустить сбор статистики (просмотры, реакции)
* `/duplicates @username` — переключить разрешение повторных картинок для админа

### Админы

* `/addadm @user` — добавить админа
* `/deladm @user` — удалить админа

### Боты

* `/addbot <BOT_TOKEN> @user` — добавить **именного бота** для админа
* `/deletebot @user` — удалить **именного бота**

## Как это работает

1. Админ присылает сообщение боту
2. Сообщение сохраняется в `messages.db`
3. Планировщик (`periodic_post`) проверяет:

   * время
   * интервал
   * наличие постов
4. Выбирается случайный админ
5. Пост публикуется от его именного бота (если есть)
6. Обновляется статистика и счётчики

## Хранение данных

### Защита от повторных картинок

Проверка общая для всех администраторов: учитывает отложку и опубликованные
посты, принятые после включения проверки. Старые посты автоматически не
индексируются. Подпись к картинке не влияет на проверку: новая подпись не
делает повтор уникальным.

Проверяются фотографии и статичные JPEG/PNG/WebP, присланные документами.
Тексты, видео и другие типы контента пока не проверяются. В альбоме каждая
статичная картинка проверяется отдельно; сравнения альбомов целиком пока нет.

Порядок проверки:

1. Поиск Telegram `file_unique_id` **до скачивания**.
2. Загрузка неизвестного изображения в оперативную память с лимитом размера.
3. Учёт EXIF-ориентации и прозрачности, вписывание в 128×128 на белом фоне.
4. Поиск точного совпадения по SHA-256 нормализованных пикселей.
5. Отбор кандидатов по 64-битным pHash и dHash: пройти должны оба порога.
6. Цветной SSIM по блокам 8×8 для максимум 32 кандидатов. Итог —
   `0.75 × среднее + 0.25 × десятый перцентиль`, порог по умолчанию `0.92`.

При совпадении бот не добавляет картинку и сообщает, что она уже в твоей
отложке (с ID сообщения), в отложке другого админа (с его именем) либо
опубликована в канале (со ссылкой). Подтверждений и кнопки обхода нет.
При ошибке скачивания/проверки картинка не принимается; можно прислать её позже.
Проверка и сохранение сериализованы между админами, включая элементы альбомов.

**Разрешение повторов.** По умолчанию включено только у главного админа.
Главный админ командой `/duplicates @username` переключает разрешение
для указанного администратора, в том числе для себя. Настройка сохраняется
по Telegram user ID в `statistics.db`. Разрешённые повторы всё равно получают
отпечатки и участвуют в проверке загрузок остальных админов.

**Миграция и хранение.** При запуске автоматически применяется идемпотентная
миграция `migrations/001_message_fingerprints.sql`. В `messages` добавляется
общее nullable-поле `content_hash`; у старых сообщений и новых сообщений
других типов оно остаётся `NULL`. Сейчас значения имеют префикс `image:v1:`.
Для картинки рядом хранятся `file_unique_id`, `image_phash`, `image_dhash`
и `image_rgb` — ровно **49 152 байта RGB 128×128 без сжатия**. Обычная загрузка
очереди не загружает RGB-данные всех постов в оперативную память.

**Оригиналы и временные файлы не записываются на диск.** Буфер скачивания
закрывается и при успехе, и при ошибке. В базе остаётся только миниатюра,
нужная для следующих сравнений. Отдельных каталогов, Redis и архивных таблиц нет.
Существующих Docker volumes для баз данных достаточно.

При удалении поста его отпечаток и миниатюра удаляются той же операцией SQLite.
Это относится и к `/clear`, и к `/delmsg`, и к `/clearposted`. Отдельных файлов,
которые могли бы остаться после удаления записи, нет. SQLite повторно использует
освобождённые страницы; размер файла базы после удаления может не уменьшиться.
История **не истекает и не вытесняется автоматически**: база растёт вместе
с количеством сохранённых постов. 10 000 картинок — около 469 МиБ RGB-данных
плюс записи, индексы и служебные страницы SQLite.

Необязательные настройки `.env` (значения по умолчанию):

```env
IMAGE_DEDUP_DOWNLOAD_BYTES=20971520
IMAGE_DEDUP_MAX_PIXELS=20000000
IMAGE_DEDUP_PHASH_DISTANCE=10
IMAGE_DEDUP_DHASH_DISTANCE=14
IMAGE_DEDUP_CANDIDATES=32
IMAGE_DEDUP_SIMILARITY=0.92
```

Схема и блочное сравнение основаны на
[TeleBOYANkeeper](https://github.com/k0stett/TeleBOYANkeeper); реализация на
Python/Pillow/NumPy, без нейросетей. Числа хешей относятся к нашей версии
нормализации, побитовая совместимость с Go-реализацией не предполагается.
Пороги проверены на тестовых изображениях с пересжатием, изменением размера,
небольшим цветовым фильтром и заменой крупной надписи. Сильная обрезка, рамки,
сильное ухудшение качества и очень мелкая замена текста остаются сложными
случаями; на реальных мемах возможны пропуски и ложные совпадения.

* **statistics.db** — статистика админов

Обе БД создаются автоматически.

## Наглядный пример введения бота в эксплуатацию

* Без использования именных ботов

    - Заполнение необходимых (*) переменных в .env
    - Добавление бота в целевой канал (в который и будет производиться публикация сообщений)
    - Настройка оставшихся переменных - временные интервалы, дополнительные админы - через команды бота
    - Админы могут присылать сообщения либо в лс боту, либо в какую-нибудь группу с ботом
    - Эксплуатируем по полной!!
* С использованием именных ботов - нужны для подписей к постам админов

    - Передумываем эксплуатировать. Сначала создаём именных ботов и называем их именами админов.
    - Добавляем именных админов в беседу:
        * Можно добавить всех админов и именных ботов в одну беседу и осуществлять "сброс" постов туда.
        * Можно создать отдельные беседы для каждого из админов. Участниками такой беседы будут:
            * Основной бот
            * Именной бот
            * Админ
    - Связываем админов с их именными ботами через /addbot
    - Все радуются, что можно эксплуатировать программу по полной и несомненно делают это!!

* **Очень важно - иначе ничего не будет работать:**
* **При добавлении ботов выдавать им админки с правом на _назначение админов_ (Add new admins)**
